Guiding principle

Merchandisers edit data (metafields, metaobjects, menus, section settings); developers ship components (sections, snippets, tokens). The two never collide. This is what keeps a luxury catalogue fast to run and cheap to evolve.

Section 01

Theme architecture & principles

  • Online Store 2.0 — JSON templates with sections everywhere, app blocks, and theme blocks. Every page is composed, not coded.
  • Metafield-driven — all editorial & spec content (materials, dimensions, care, guides, FAQs) comes from metafields/metaobjects with dynamic sources, so nothing is hardcoded in Liquid.
  • Component model — one concern per section, one partial per snippet; sections own their `{% schema %}`, their scoped CSS asset, and their optional web-component JS.
  • Design tokens first — a single `tokens.css` mirrors the Art Avenue design system (ivory/stone/bronze/charcoal, Cormorant Garamond + Jost, spacing, radii, motion). Every component reads tokens; no raw hex in components.
  • App-light — avoid script-injecting apps; prefer native OS 2.0 + Storefront APIs to protect performance and luxury polish.

CSS architecture

Cascade layers keep specificity predictable and overrides safe:

/* base.css — load order via @layer */
@layer tokens, base, layout, components, utilities;

@layer tokens   { /* tokens.css — custom properties only */ }
@layer base     { /* reset, typography, color schemes */ }
@layer layout   { /* container, grid, section spacing */ }
@layer components { /* per-component css, loaded per section */ }
@layer utilities { /* spacing/visibility helpers */ }

Critical CSS (tokens + base + layout) is inlined in <head>; component CSS loads per section via {{ 'aa-product-gallery.css' | asset_url | stylesheet_tag }} so a page only ships the CSS it uses.

JavaScript strategy

  • Web components, one behaviour each: <aa-cart-drawer>, <aa-predictive-search>, <aa-sticky-atc>, <aa-rug-guide>, <aa-variant-picker>, <aa-quick-view>.
  • All defer, section-scoped, hydrated on interaction/visibility. No framework, no jQuery.
  • Cart & quick-view use the Section Rendering API for HTML-over-the-wire updates.

Snippet architecture

Snippets are pure, parameterised partials — rendered with explicit args ({% render %}, never include) for isolated scope.

SnippetResponsibility
aa-product-cardEditorial 4:5 card — image, badge, name, price, save. Used in every grid/rail.
aa-collection-tileFull-bleed category tile with scrim + CTA.
aa-priceMoney formatting, compare-at, "from", per-variant.
aa-imageResponsive image_url + srcset + aspect-ratio box (no CLS).
aa-swatchesFinish/upholstery swatches from variant + metaobject.
aa-badgeNew / Made to Order / Best Seller / Handcrafted.
aa-eyebrowLetterspaced section label.
aa-whatsapp-ctaBuilds wa.me link with title + SKU + URL pre-fill.

aa-iconInline SVG sprite reference.
aa-metafield-rteSafely renders rich-text metafields.

Rule

If markup appears in two sections, it becomes a snippet. Snippets take data as arguments and read tokens for style — they never query global state.

Product template architecture

One template suffix per product type, assigned in admin (or by automation). Each composes aa-main-product with the right blocks plus type-specific guide sections — all reading metafields.

TemplateAdds (beyond core PDP)
product.furnituresize/finish/material/upholstery variants · Fabric/Finish Sample · Wood & Finish & Upholstery guides · customization CTA
product.rugsize + backing + material variants · Rug Size + Placement + Material guides
product.cushionsize + cover/fill variants (live price) · Cushion size guide · styling suggestions
product.lightingfinish + size + bulb/voltage spec · install note
product.wall-artsize + frame + medium variants · hang-height visual

Core PDP block order (aa-main-product)

gallery → vendor → title → price → variant-picker → quantity
→ buy-buttons → sticky-atc → whatsapp-cta → sample/customization
→ trust-row → delivery → accordion(materials · craft · dimensions · care)

Below the buy area, page-level sections: aa-guides → aa-complete-the-room → aa-designer-recs → aa-faqs → aa-recently-viewed. Sticky ATC + WhatsApp are persistent on mobile via <aa-sticky-atc>.

Variant strategy

Real purchasable choices = native variants (price/image/inventory/lead-time). Many finishes → drive variant images from an aa.swatch metaobject rather than exploding the matrix. "Custom size/finish" is not a variant — it's the WhatsApp/enquiry CTA.

Collection template architecture

  • collection.json — banner (metafield hero + intro) → aa-shop-by row → aa-facets (sticky sidebar / mobile bottom-sheet) + grid → aa-merch-block interrupts → related collections.
  • collection.rugs.json — adds Shop by Size / Room / Colour / Pattern / Material and a Rug Size Guide entry banner.
  • Filtering — Shopify native storefront filters (Search & Discovery), driven by product options, tags & metafields; URL-encoded, server-rendered, crawlable.
  • Sort — featured, newest, price; preserved on back-navigation.
  • Quick view — <aa-quick-view> via Section Rendering API; save-for-later via localStorage + customer metafield when logged in.

Merchandising

One lifestyle / "Shop the Look" interrupt every ~6 products; aa-shop-by tiles let buyers self-select into a confident subset before scrolling the grid — the core discovery + decision-fatigue lever.

Navigation architecture

  • Source — Shopify navigation linklists for structure; a menu_feature metaobject supplies each mega-menu's imagery, designer picks & promo tile (no hardcoding).
  • Mega-menu (aa-header blocks) — per top-level item: By Type columns · Shop by Room · Shop by Style/Material · Discover (New / Best Sellers / Designer Favourites) · one featured visual.
  • Cross-cutting routes — Room / Style / Material / Size resolve to filtered collection URLs, reused on collection pages.
  • Mobile — <aa-nav-drawer> accordion mirroring the same linklists; Trade & account pinned; persistent search & WhatsApp.
  • Utility — predictive search, account, wishlist, cart (live count); slim trust bar above header.

Search architecture

  • Predictive search — <aa-predictive-search> against the Predictive Search API; results show product imagery, collections, pages & articles with the brand's editorial card.
  • Full results — search.json reuses aa-facets + grid, so filtering/sorting matches collections exactly.
  • Relevance — synonyms, redirects & boosts managed in Search & Discovery (e.g. "dhurrie" → rugs, "couch" → sofas).
  • Filters in search — type, material, room, price; same filter snippet as collections.
  • Empty & zero-results — curated "explore" tiles + WhatsApp consultant prompt, never a dead end.

GitHub workflow

Shopify's GitHub integration binds themes to branches; the repo is the source of truth.

BranchBound theme
mainProduction (the live theme) — protected, PR-only
stagingStaging theme — QA & stakeholder review
feat/*Unpublished preview themes per feature (CLI-pushed)
 
# branch → build → preview → review → merge
git checkout -b feat/rug-size-guide
shopify theme dev          # local hot-reload
shopify theme push -u -t "feat-rug-size-guide"  # preview theme
# open PR → CI runs → review preview link → squash-merge to main
  • Branch protection on main: required PR review + green CI before merge.
  • Editor changes (merchandiser JSON template/settings edits) sync back to the bound branch — pull regularly to avoid drift: shopify theme pull.
  • Conventional commits + CHANGELOG; one feature per PR.

Deployment workflow

# shopify.theme.toml — environments
[environments.development]
store = "art-avenue.myshopify.com"
theme = "<dev-theme-id>"
[environments.staging]
store = "art-avenue.myshopify.com"
theme = "<staging-theme-id>"
  • Local — shopify theme dev for hot-reload against a dev theme.
  • Promote — merge to main; GitHub integration deploys to the live theme automatically (no manual upload).
  • Rollback — revert the commit (or restore a prior theme version); Git history = deploy history.
  • Secrets/config — no secrets in theme; storefront tokens via app proxy if ever needed.

CI — .github/workflows/ci.yml

- Theme Check      # Liquid lint, schema, a11y, perf hints
- Prettier/ESLint  # liquid + js + css formatting
- Lighthouse CI    # perf/SEO/a11y budgets on preview URL
- Broken-link & image-weight checks

Quality gate

A PR cannot merge unless Theme Check passes and Lighthouse meets budgets (LCP, CLS, TBT). Performance is enforced, not hoped for.

Scalability & performance

Core Web Vitals

  • Inline critical CSS; defer the rest via per-section assets.
  • Responsive image_url + srcset + loading="lazy" + reserved aspect ratios (zero CLS).
  • preconnect + font-display:swap; self-host woff2 for Cormorant + Jost.
  • Defer all JS; hydrate components on view/interaction.
  • Budget: LCP < 2.5s, CLS < 0.1, INP < 200ms on 4G mobile.

Scale & maintainability

  • Metafields/metaobjects = no redeploy to add content.
  • Template suffixes scale to new product types without touching core.
  • Tokens make a palette/type change a one-file edit.
  • Section presets let merchandisers build new pages unaided.
  • i18n-ready via locales/ for international buyers.
  • App-light keeps third-party JS — the usual perf tax — near zero.

The throughline

Speed and calm are the luxury. This architecture makes the fast path the default: small components, structured content, enforced budgets, and a Git-backed workflow a product team can run for years.
